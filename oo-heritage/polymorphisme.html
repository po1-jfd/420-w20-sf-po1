Polymorphisme ​

Le polymorphisme permet de traiter différents types d'objets de manière uniforme via leur type commun. Une même instruction peut produire des comportements différents selon le type réel de l'objet.

  • Utiliser un type parent pour référencer un objet enfant
  • Expliquer la résolution dynamique des méthodes
  • Distinguer surcharge (overloading) et redéfinition (overriding)

Polymorphisme par substitution ​

Partout où une superclasse est attendue, une sous-classe peut être utilisée. C'est le principe de substitution de Liskov.

java
public class Animal {
    protected String nom;

    public Animal(String nom) {
        this.nom = nom;
    }

    public void parler() {
        System.out.println(this.nom + " fait un son.");
    }
}

public class Chien extends Animal {

    public Chien(String nom) {
        super(nom);
    }

    @Override
    public void parler() {
        System.out.println(this.nom + " aboie : Ouaf!");
    }
}

public class Chat extends Animal {

    public Chat(String nom) {
        super(nom);
    }

    @Override
    public void parler() {
        System.out.println(this.nom + " miaule : Miaou!");
    }
}
java
// Une variable de type Animal peut référencer un Chien ou un Chat
Animal a1 = new Chien("Rex");
Animal a2 = new Chat("Minou");
Animal a3 = new Animal("Inconnu");

// La méthode appelée dépend du type RÉEL de l'objet, pas du type de la variable
a1.parler();  // "Rex aboie : Ouaf!"
a2.parler();  // "Minou miaule : Miaou!"
a3.parler();  // "Inconnu fait un son."

Résolution dynamique (dispatch) ​

Java résout les appels de méthodes à l'exécution selon le type réel de l'objet, pas le type déclaré de la variable. On appelle cela le late binding ou dynamic dispatch.

java
ArrayList<Animal> animaux = new ArrayList<>();
animaux.add(new Chien("Rex"));
animaux.add(new Chat("Minou"));
animaux.add(new Chien("Buddy"));

// Chaque appel appelle la bonne version selon le type réel
for (Animal a : animaux) {
    a.parler();  // polymorphisme en action !
}
// Rex aboie : Ouaf!
// Minou miaule : Miaou!
// Buddy aboie : Ouaf!

Surcharge vs Redéfinition ​

Surcharge (Overloading)Redéfinition (Overriding)
MécanismeMême nom, signatures différentesMême signature, dans une sous-classe
RésolutionÀ la compilationÀ l'exécution
@OverrideNonOui (obligatoire dans ce cours)
ClasseMême classeClasse parente et sous-classe
java
// Surcharge - même classe, signatures différentes
public class Calculatrice {
    public int calculer(int a, int b) { return a + b; }
    public double calculer(double a, double b) { return a + b; }
    public int calculer(int a, int b, int c) { return a + b + c; }
}

// Redéfinition - sous-classe, même signature
public class CalculatriceScientifique extends Calculatrice {
    @Override
    public int calculer(int a, int b) {
        // comportement différent dans la sous-classe
        return Math.abs(a + b);
    }
}

Contrats sémantiques ​

Le polymorphisme n'est valide que si la sous-classe respecte le contrat sémantique de la superclasse. Si une méthode redéfinie change le sens du comportement attendu, le polymorphisme est brisé.

java
// Exemple d'infraction sémantique : Rectangle et Carré
public class Rectangle {
    public void setLargeur(double largeur) { this.largeur = largeur; }
    public void setHauteur(double hauteur) { this.hauteur = hauteur; }
}

public class Carre extends Rectangle {
    @Override
    public void setLargeur(double largeur) {
        this.largeur = largeur;
        this.hauteur = largeur;  // force hauteur == largeur
    }
    // Problem : un Carré enfreint le contrat de Rectangle !
    // Code qui suppose que setLargeur() n'affecte pas la hauteur sera surpris.
}

Principe de substitution de Liskov

Une sous-classe ne devrait jamais "surprendre" le code qui l'utilise via son type parent. Si tu dois redéfinir une méthode de façon à enfreindre les attentes de la superclasse, l'héritage n'est probablement pas la bonne relation.
