Revues de code ​

La revue de code est le processus par lequel des développeurs examinent le code des autres pour trouver des problèmes, partager des connaissances et améliorer la qualité collective du code.

Objectifs d'apprentissage ​

Après cette section, tu seras capable de...

  • Expliquer la valeur des revues de code dans un contexte professionnel
  • Donner et recevoir des commentaires de code de façon constructive
  • Identifier les aspects à vérifier lors d'une revue de code
  • Distinguer les problèmes critiques des suggestions stylistiques

  • Expliquer la valeur des revues de code dans un contexte professionnel

Pourquoi les revues de code ? ​

  • Détection d'erreurs : un deuxième regard voit des problèmes que l'auteur a ratés
  • Partage de connaissance : toute l'équipe comprend le code, pas seulement l'auteur
  • Cohérence : le style et les pratiques sont uniformes dans le projet
  • Apprentissage mutuel : les développeurs apprennent les uns des autres

Ce qu'on vérifie dans une revue ​

Exactitude ​

  • Le code fait-il ce qu'il est censé faire ?
  • Les cas limites sont-ils gérés ?
  • Les exceptions sont-elles lancées au bon endroit ?

Lisibilité ​

  • Les noms sont-ils expressifs ?
  • Les méthodes sont-elles courtes et à responsabilité unique ?
  • Y a-t-il de la duplication évitable ?

Conception ​

  • Les responsabilités sont-elles bien réparties (SRP) ?
  • Le code respecte-t-il Tell Don't Ask et la loi de Déméter ?
  • Y a-t-il des code smells (God class, méthode trop longue, etc.) ?

Tests ​

  • Les cas limites sont-ils testés ?
  • Les noms de tests décrivent-ils bien les comportements ?
  • Les tests sont-ils isolés et déterministes ?

Donner des commentaires constructifs ​

Commenter le code, pas la personne

"Cette méthode fait deux choses, on pourrait l'extraire en deux méthodes distinctes." -pas - "Tu écris du mauvais code."

Ton neutre et précis ​

Avant : "C'est illisible."
Après : "La méthode `traiterDonnees()` est difficile à suivre car elle mélange
         la validation et le calcul. On pourrait extraire une méthode `valider()`."

Proposer une alternative ​

"Je suggère d'utiliser une énumération ici plutôt que des entiers,
 car cela empêche les valeurs invalides au moment de la compilation."

Distinguer priorité et préférence ​

CRITIQUE : "Cette condition inverse la logique - elle laisse passer les données invalides."
SUGGESTION : "Je préférerais `estValide()` à `pasInvalide()` pour la lisibilité."
QUESTION : "Pourquoi utilises-tu un ArrayList ici plutôt qu'un Set ?"

Recevoir des commentaires ​

  • Écouter sans se défendre immédiatement
  • Poser des questions pour comprendre le commentaire
  • Distinguer les opinions personnelles des problèmes réels
  • Remercier - la revue de code est un service rendu, pas une attaque

Le code n'est pas ton identité

Un commentaire sur ton code n'est pas un jugement sur toi. Les développeurs expérimentés reçoivent des revues de code tous les jours - c'est une pratique normale, pas un signe de faiblesse.

Tribunal du Code - format pédagogique ​

Dans ce cours, le "Tribunal du Code" est un exercice où on examine des extraits de code réels et on débat de leur qualité. Pour chaque cas :

  1. L'accusation : quelle règle est potentiellement non-respectée ?
  2. La défense : y a-t-il une justification valable ?
  3. Le verdict : faut-il corriger ? Comment ?

Ce format développe le jugement professionnel : reconnaître que les règles sont des guidelines avec des exceptions justifiées, pas des absolus.
